1 · The big idea

One sentence: log in once in a central place, then reach every app you're allowed to — without any app being able to see another app's data.

Imagine a company runs many separate apps (here we call them tenants: Tenant A and Tenant B). Today, the painful "before" world looks like this:

The problem (before): every app keeps its own list of usernames and passwords. A person who uses 3 apps needs 3 accounts, 3 passwords, 3 login pages. Annoying for users, and a security headache (passwords copied everywhere).

This project fixes that with one rule, worth memorizing:

Centralize authentication. Keep authorization local.
AUTHENTICATION

"Who are you?"

Done in one central place — the IdP (Identity Provider). It is the only service that ever checks a password.

AUTHORIZATION

"What are you allowed to do here?"

Decided by each tenant, on its own, against its own database. A tenant never checks passwords — it only checks permission.

Analogy — a music festival. You show your ID once at the main gate (the IdP) and get a wristband (a token). Each stage (a tenant) just glances at your wristband to see if you're allowed in — they don't re-check your ID, and they can't let you into a stage your wristband doesn't cover. The wristband is hard to fake because it has a special mark only the main gate can make.

2 · OAuth and Single Sign-On, in plain words

These two terms get mixed up constantly. Here's the simple version, then how this project relates to them.

Single Sign-On (SSO) — the experience

SSO means: you log in once, and you're now logged into many apps. You don't type your password again at each app. That's it — SSO is about the user experience of "one login, many doors."

Analogy: your office keycard. You badge in once at the front door; after that the same card opens the gym, the parking garage, and the cafeteria. You didn't re-register at each door.

OAuth (and its cousin OIDC) — the rulebook

OAuth 2.0 is a standard set of rules for how apps hand out and accept access without sharing your password. OpenID Connect (OIDC) is a small layer on top of OAuth that adds "and here's proof of who the user is." Together they're the most common way real systems build SSO.

The key OAuth idea: instead of giving an app your password, a trusted central server gives the app a token — a temporary, limited pass. The app trusts the token, not your password.

How this prototype relates to the standards. Real production SSO uses the full OAuth/OIDC redirect dance (your browser bounces to the login site and back, with cookies). This prototype keeps the same trust model — a central issuer mints a signed token, each app verifies it — but skips the browser redirects to stay small. So you're learning the engine of OAuth/SSO without the extra plumbing. The production version (Cognito / OIDC authorization-code flow) is described in the architecture docs as the next step.
Why not just share the password with each app? Because then every app could store, leak, or misuse it — and you'd have to trust all of them equally. Tokens are better: they expire, they say exactly what you're allowed to do, and an app holding one still can't recover your password. That's the whole reason OAuth exists.

3 · What is a JWT? (the token that makes it work)

A JWT (JSON Web Token, say "jot") is the wristband. It's a small piece of text that carries facts about you and a tamper-proof signature.

A JWT has three parts joined by dots: header.payload.signature

// 1) HEADER — how the token is signed
{ "alg": "RS256", "kid": "<key id>", "typ": "JWT" }

// 2) PAYLOAD — the facts ("claims") about you
{
  "iss": "https://auth.platform.local",  // who issued it (the IdP)
  "aud": "platform-tenants",             // who it's for (the tenants)
  "sub": "u_8f3a...",                    // your stable GLOBAL user id
  "exp": 1700000900,                     // expires after 15 min
  "email": "alice@example.com",
  "entitlements": {                      // ⭐ which tenants you may enter
    "tenant_a": ["member"]
  }
}

// 3) SIGNATURE — a math seal only the IdP can create

The signature is the magic

The IdP signs the token with a private key that only it has. Anyone can check the seal using the matching public key (which is shared freely). This is called RS256 / asymmetric signing.

🔒 Private key — secret, lives only at the IdP.
Used to create (sign) tokens. If leaked, attackers could forge tokens.
🔓 Public key — shared openly (via JWKS).
Used to check tokens. Safe to publish; it can verify but not forge.
Why a public/private pair instead of one shared password? If every tenant knew the same secret used to make tokens, any one hacked tenant could forge tokens for all the others. With RS256, tenants only get the public key — enough to verify, never enough to forge. The power to mint tokens stays in exactly one place.
Analogy: a wax seal on a royal letter. Only the king's ring (private key) can stamp it; anyone with a picture of the seal (public key) can confirm it's real, but they can't make their own.

JWKS — where the public key is published

JWKS (JSON Web Key Set) is just a web page at /.well-known/jwks.json that lists the IdP's public keys. Each tenant downloads it once and remembers (caches) it. The kid ("key id") in the token header tells a tenant which key to use, which makes rotating keys possible later.

4 · Key components (the pieces)

The whole system is just three running services plus some shared code. Here's each piece and the file where it lives.

PORT 8000

Auth service = the IdP (the central login)

The only place passwords are checked. It does two jobs:

  • POST /login — check email + password, then mint (create & sign) a JWT.
  • GET /.well-known/jwks.json — publish the public key so tenants can verify tokens.
  • POST /signup — (demo extra) create a new global account + entitlements.

Code: auth_service/app.py · Data it owns: identities (humans + password hashes) and entitlements (who may enter which tenant).

PORTS 8001 & 8002

Tenant service ×2 = the apps (Tenant A, Tenant B)

The same program run twice with a different TENANT_ID and database. It never checks passwords. It only:

  • Verifies the token offline (using the cached public key).
  • Checks the token's entitlements include this tenant.
  • Serves only its own data: GET /me, GET /data, GET /healthz.

Code: tenant_service/app.py · Data it owns: local users (linked to the global id via idp_sub) and data_items.

SHARED

Common code (used by everyone)

  • common/jwt_tokens.py — the security-critical file. mint() (runs only in the IdP) and verify() (runs in every tenant).
  • common/config.py — pinned constants: issuer, audience, RS256, 15-min token life, 60-second clock leeway.

The demo UI (what you may have open)

web/index.html is a small browser page that lets you log in, see the decoded token, and click buttons to call each tenant — so you can watch the same token get accepted by one tenant and refused by another.

"One image, many roles"

There is one Docker image. The docker-compose.yml file decides what each container becomes by passing a different command and TENANT_ID. This mirrors real life: every tenant runs the identical app, just pointed at its own database.

5 · The flows (how the pieces talk)

Follow the token. Everything is "get a token from the IdP, then show it to a tenant."

Flow A — Log in once, use it everywhere (the happy path)

1
User → IdP: sends email + password to POST /login.
2
IdP: checks the password with bcrypt, reads the user's entitlements, and mints a signed JWT.
3
IdP → User: returns the token. The user now holds the wristband.
4
User → Tenant A: calls GET /me with header Authorization: Bearer <token>.
5
Tenant A: verifies the signature with the cached public key, checks entitlements, finds the local user, returns 200 with its own data.
6
User → Tenant B: shows the same token. No second login needed — that's SSO.
           one login                  same token, many apps
  User ───▶ IdP (8000) ───token───▶ User ───▶ Tenant A (8001)  200 ok
                                       └──▶ Tenant B (8002)  depends on entitlements
            (only place that
             checks passwords)

Flow B — A token that shouldn't work here (isolation)

Alice is entitled to tenant_a only. She shows her valid token to Tenant B:

  Alice's token ──▶ Tenant B:  signature is valid ✔
                              but entitlements = { tenant_a } — no "tenant_b"
                              ▶ 403 not entitled  (before any data is read!)

This is the isolation invariant — the single most important rule. Even a perfectly valid token is refused if it doesn't name this tenant.

Flow C — "Entitled, but not yet provisioned" (the subtle one)

A brand-new signed-up user is allowed into Tenant A (entitlement says so), but Tenant A has no local users row for them yet. So:

  new user ──▶ Tenant A /me  ▶ 403 no local user   entitlement ≠ provisioning
  click "Provision here"     ▶ tenant creates the local row
  new user ──▶ Tenant A /me  ▶ 200 ok
Lesson: being allowed in (entitlement, decided centrally) is not the same as having an account here (a local row, owned by the tenant). Real systems "provision" the local account just-in-time on first visit.

6 · The 6 security checks (the heart of it)

Every time a tenant receives a request, it runs these checks in this exact order. The first one that fails decides the error code. Memorize this table — it's the contract.

#Check (in plain words)If it fails
1Is there a proper Authorization: Bearer <token> header?401 missing token
2Is the signature real, and made with RS256? (pinned!)401 invalid token
3Is the token still in date (not expired, allowing ±60s)?401 token expired
4Right issuer (iss) and audience (aud)?401 invalid token
5Do the entitlements name THIS tenant? ⭐403 not entitled
6Does sub match a local user row here?403 no local user
✓All passed → serve this tenant's data200 ok
401 vs 403 — know the difference (a classic interview question):
401 = "I don't know who you are" (authentication failed — bad/expired/forged token).
403 = "I know who you are, but you're not allowed here" (authorization failed).
Why is step 5 (403) before any database read so important? Because it means a token for Tenant A can never even touch Tenant B's data — the request is rejected at the door, before a single query runs. That's how "one login for many apps" stays safe: convenience for users, but airtight isolation between tenants.
Why "pin RS256" in step 2? Old JWT bugs let attackers change the header to alg: none ("no signature, trust me") or trick a server into using the public key as a shared password (HS256 confusion). By only accepting RS256 and nothing else, those attacks are dead on arrival. In code it's literally algorithms=["RS256"] — never relax it.

7 · Why each feature exists

Every design choice here is answering a real-world "what if?" Here they are as question → answer.

FeatureThe worry it answers
Central IdP (one login)"Users hate 3 passwords; copied passwords leak." → One account, one password, one place to secure.
Entitlements inside the token"What if the IdP is slow or down on every request?" → The token already says what you may access, so tenants don't call the IdP per request.
Offline verification (cached public key)"What if the IdP goes down?" → In-flight users keep working; only new logins are blocked. (Fail-open for validation, fail-closed for new auth.)
RS256 (public/private keys)"What if one tenant gets hacked?" → A hacked tenant only has the public key — it can verify but never forge tokens for others.
Short token life (15 min)"What if a token is stolen?" → It expires fast, limiting the damage window.
Same 401 for unknown email & wrong password"Can an attacker learn which emails are registered?" → No — both fail identically, even taking the same time (dummy hash compare).
Step-5 isolation check before any DB read"Could a valid token peek at another tenant's data?" → No — it's rejected before any query runs.
Local users + idp_sub"How do tenants keep their own profiles/roles?" → They keep their local row and just add a link (idp_sub) to the global identity.
Reading tip: the project records each of these decisions as an ADR (Architecture Decision Record) in docs/adr/ — a short document saying "we decided X, because Y, and the trade-off was Z." Great practice for any serious codebase.

8 · How it's implemented (the code, gently)

You don't need to be a Python expert. Here are the few snippets that matter, with the idea explained next to them.

Minting a token (IdP only)

token = pyjwt.encode(payload, private_key_pem,
                     algorithm="RS256",      # sign with the secret key
                     headers={"kid": kid})   # say which key was used

The payload holds iss, aud, sub, exp, email, entitlements. Only the IdP has private_key_pem, so only the IdP can do this.

Verifying a token (every tenant)

pyjwt.decode(token, key=public_key,
             algorithms=["RS256"],        # ⭐ pin — rejects none / HS256
             issuer=ISSUER, audience=AUDIENCE,
             leeway=60,                   # allow 60s clock difference
             options={"require": ["exp","iat","iss","aud","sub"]})

This single call performs checks 2, 3 and 4. If anything is off, it raises an error and the tenant returns 401.

The isolation check (step 5)

entitlements = claims.get("entitlements", {})
if tenant_id not in entitlements:
    raise HTTPException(status_code=403, detail="not entitled")  # before any DB read

No password enumeration (login)

if identity is None:
    bcrypt.checkpw(password, _DUMMY_HASH)   # waste the same time on a fake hash
    raise HTTPException(401, "invalid credentials")
if not bcrypt.checkpw(password, identity["password_hash"]):
    raise HTTPException(401, "invalid credentials")   # identical error

Unknown email and wrong password look and feel the same to an attacker — no hint about which emails exist.

The factory pattern (why tests are easy)

Each service is built by a create_app(...) function that takes its database and keys as arguments. Production wiring (asgi.py) passes the real disk paths; tests pass a tiny temporary database and a throwaway key pair. Same code, swappable parts — that's why this project can test the whole security pipeline in milliseconds without Docker.

9 · Migration — moving the old world into the new one

The apps already existed with their own users tables. How do you move to central login without downtime? That's what migrate.py does.

For each existing local user it:

  1. Creates (or reuses) a global identity in the IdP, matched by email — so the same person across two tenants becomes one global account.
  2. Grants the entitlement for that tenant.
  3. Stamps idp_sub back onto the local row, linking local ⇄ global.
Why "idempotent"? You can run it again and again safely — already-linked rows are skipped, no duplicates appear. That's what lets you roll out one tenant at a time, pause, and resume, with nothing breaking. Safe migrations are restartable migrations.

10 · How to run it yourself

All commands live in the Makefile. The fastest learning loop:

CommandWhat it does
make venvOne-time setup: create the Python environment.
make testRun fast unit tests on your machine (no Docker). Great for reading + tweaking.
make upBuild & start all 3 services in Docker (auth :8000, tenant_a :8001, tenant_b :8002).

Best way to learn: run make up, then open web/index.html and click around. Log in as alice (tenant_a only) and watch Tenant B reject her with 403 not entitled. Then log in as bob (both tenants) and watch both return 200 — each with its own data. That single contrast is the whole project.
Suggested experiments:
  • Log in, wait 15 minutes, call a tenant → watch it become 401 token expired.
  • Sign up a brand-new user, call a tenant → 403 no local user, then click Provision here → 200.
  • Open the token in the UI and read its decoded claims — find entitlements yourself.

11 · Glossary (quick reference)

Authentication
Proving who you are (checking a password). Done by the IdP.
Authorization
Deciding what you may do. Done by each tenant.
IdP (Identity Provider)
The central login server; the only place passwords are verified.
Tenant
One app/customer workspace with its own database. Trusts tokens, never checks passwords.
SSO (Single Sign-On)
Log in once, use many apps without logging in again.
OAuth 2.0
The standard rulebook for handing out access tokens instead of passwords.
OIDC
OAuth plus identity info ("who is this user"). The common foundation of modern SSO.
JWT
A signed token carrying claims about you; the wristband.
Claim
A fact inside a JWT (e.g. sub, email, entitlements).
Bearer token
A token where simply holding it grants access; sent as Authorization: Bearer ....
RS256
Asymmetric signing: a secret private key signs, a public key verifies.
JWKS
The public web page listing the IdP's public keys, so tenants can verify offline.
Entitlement
A grant saying "this identity may access this tenant" (with roles).
Provisioning
Creating the tenant-local user row. Being entitled ≠ being provisioned.
idp_sub
The column in a tenant's local users table that links to the global identity (sub).
Isolation invariant
The rule that a token must never read a tenant it isn't entitled to — enforced before any DB read.

12 · Quick self-quiz

Try to answer before expanding. If you can do these, you understand the project.

1. Which service is allowed to check passwords, and why only that one?

Only the IdP (auth_service). Centralizing it means one place to secure, one password per human, and tenants never store credentials. "Centralize authentication."

2. A token is perfectly valid but a tenant returns 403. What happened?

Authorization failed, not authentication. Either step 5 (the token's entitlements don't name this tenant → "not entitled") or step 6 (no local user row here → "no local user").

3. Why give tenants only the public key?

So a compromised tenant can verify tokens but never forge them. The forging power (private key) stays solely at the IdP. This is the point of RS256.

4. The IdP goes down. Can existing users still use the tenants?

Yes — for in-flight tokens. Tenants verify offline with the cached public key, so they don't need the IdP per request. Only new logins (minting tokens) are blocked.

5. How is this project related to OAuth and SSO?

It implements the core engine of OAuth/OIDC-style SSO: a central issuer mints a signed token, each app verifies and trusts the signature instead of asking for a password. It skips the browser redirect dance to stay simple, but the trust model is the same.

6. Why must the entitlement check run before any database query?

So a token for Tenant A can never even touch Tenant B's data. Rejecting at the door (step 5, 403) is what keeps "one login, many apps" safe — the isolation invariant.
