Single Point of Authentication

System design reference — log in once, reach every entitled tenant, without breaking tenant data isolation.

Principle Before / After Components Login flow The token Validation Trust boundary Fail open/closed Migration

01 Core principle

The one idea the whole design hangs on.

Centralize authentication. Keep authorization local.
A central Identity Provider (IdP) proves who you are and which tenants you may reach. Each tenant decides what you can do against its own data. The IdP never touches tenant business data; tenants never authenticate users themselves.

02 Where identity lives — before vs. after

What moves to the center, and what stays in the tenant.

 Before (today)After (this design)
CredentialsDuplicated in each tenant's users tableCentral IdP — one record per human
Password checkEach tenant's PHP appCentral IdP only
SessionPHP/Apache container, per tenantStateless JWT held by the client
Cross-tenant linkNone — N logins per personentitlements claim in the token
Tenant's jobAuthenticate + authorizeAuthorize + resolve only (idp_sub)

Tenants keep their users table for local identity (profile, local roles) and gain one column — idp_sub — linking the local row to the global identity.

04 Login & access flow

One login yields a credential that opens every entitled tenant.

sequenceDiagram autonumber actor U as User participant I as Central IdP participant A as Tenant A participant B as Tenant B U->>I: POST /login (email, password) I->>I: verify bcrypt hash · read entitlements I-->>U: signed JWT {sub, entitlements:{A,B}, exp} Note over U,B: same token, no second login U->>A: GET /data (Bearer JWT) A->>A: verify signature (cached key) · check exp/iss/aud · A in entitlements? A->>A: resolve sub → local user (idp_sub) A-->>U: 200 tenant A data U->>B: GET /data (same Bearer JWT) B->>B: verify · B in entitlements? · resolve locally B-->>U: 200 tenant B data
If the token's entitlements did not include a tenant, that tenant returns 403 — the isolation invariant, enforced before any data is read.

05 The credential — a signed JWT

Self-contained: the tenant trusts the signature, not the IdP's uptime.

// header
{ "alg": "RS256", "kid": "key-2026-06" }   // asymmetric — tenants verify, never sign

// payload
{
  "iss": "https://auth.platform.example",  // issuer  — tenant checks
  "aud": "platform-tenants",             // audience — tenant checks
  "sub": "u_8f3a…",                      // stable GLOBAL user id
  "iat": 1700000000,
  "exp": 1700000900,                       // short TTL ~5–15 min
  "jti": "tok_4b1c…",                    // unique id (future revocation)
  "entitlements": {                       // which tenants + roles
    "tenant_a": ["member"],
    "tenant_b": ["admin"]
  }
}

06 What the tenant checks (every request, offline)

No call to the IdP on the hot path — only a cached public key.

  1. Extract Authorization: Bearer <jwt> 401 if missing
  2. Verify signature with cached public key, algorithm pinned to ["RS256"] — rejects alg:none & HS256 confusion 401
  3. Check exp / nbf (±60s skew), iss, aud 401
  4. Is this tenant_id in entitlements? 403 if not
  5. Resolve sub → local users row via idp_sub 403 if no mapping
  6. Serve against this tenant's DB only 200
Isolation invariant: a token whose entitlements does not name tenant X MUST NOT read tenant X's data. Enforced at step 4 — the single most important test.

07 Trust boundaries

Who trusts whom — and who can never forge a token.

flowchart TD KMS["🔑 Trust ANCHOR
IdP private signing key (KMS)
never leaves identity account"] KMS == "signs every token" ==> TOK["Signed JWT"] TOK --> A["Tenant A
verifies with PUBLIC key"] TOK --> B["Tenant B
verifies with PUBLIC key"] A -. "NO mutual trust" .-x B
IdP = root of trust
Private key signs every token, lives in KMS. A compromise of any tenant cannot forge a token — tenants hold only the public key.
Tenants never trust each other
A token scoped to A is rejected by B via aud + entitlements. Each tenant queries only its own DB. Trust is one-way: IdP → tenant.

08 If the IdP is down — fail open vs. closed

Offline validation lets in-flight traffic survive an outage; identity is never invented.

ScenarioBehaviorWhy
Valid, unexpired token in handFAIL OPEN — serveVerified offline with cached key; IdP not on hot path
Token expired / new loginFAIL CLOSED — denyIdentity cannot be minted without the IdP. Never invent identity
Tenant boots while IdP unreachableServe from cached keyKey availability must not depend on a live IdP
Net: IdP availability gates new authentication, not steady-state validation. An outage degrades gracefully — bounded in time (one token TTL), not by taking all 50 tenants down at once.

No forced re-auth
Existing PHP sessions stay valid until natural expiry; only new logins route through central auth.
Instant rollback
Flip the per-tenant flag back to local auth. Local tables stay intact via dual-write, so rollback is lossless.
Hard part — identity reconciliation: the same human is separate rows across tenants. Merge only on verified email into one global identity; unverified/mismatched → keep separate, offer account-linking.
